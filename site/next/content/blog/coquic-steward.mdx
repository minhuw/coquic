CoQUIC's main branch now receives commits that no human wrote, reviewed, or pushed. Before each one landed, it passed a whitespace check, a full build and test run, a lint pass, an independent agent review with zero findings — and then passed all of it again after being rebased onto the latest main. The system that does this is called CoQUIC Steward, and it fits in a single Python package running on one machine.

This post explains how Steward works and, more importantly, why it is built the way it is. The short version: getting an agent to produce a patch is the easy part. The hard part is deciding who gets to decide.

## Maintenance is the new bottleneck

CoQUIC is an experiment in LLM-generated systems software — the QUIC implementation, tests, and tooling are all agent-generated, with humans setting direction and judging evidence. [Why CoQUIC?](/blog/why-coquic) covers that premise.

Once the initial implementation existed, the daily work changed shape. It was no longer "build the recovery subsystem." It was: CI failed on main overnight. CodeQL opened a new alert. An interop run regressed against another implementation. Someone filed a small feature issue.

Each of these tasks has two properties that make it a perfect target for automation. It is narrowly scoped, and it arrives with its own evidence attached — a failing run ID, an alert with a file and line, an issue number. Yet handling one still meant a human writing a prompt, running an agent, reading the diff, and merging. I was spending my time being a job scheduler. That is a role software is quite good at.

## Why not just cron an agent?

The naive version of Steward is a cron job: every hour, ask an agent to "fix whatever is broken" and push the result. Nobody should run that, and the reasons why shape the entire design:

- An agent with push access can rewrite history, and one bad `git push --force` costs more than a month of automated fixes saves.
- An agent asked to "make CI green" will find the shortest path to green — which is sometimes deleting the test, weakening the CodeQL config, or marking the workflow as optional.
- An agent that watches its own dashboards will happily create the same task fifteen times for the same recurring failure.
- And when something goes wrong at 3 a.m., "the agent did something" is not an acceptable incident report.

So Steward is not an agent with credentials. It is a control loop around agents, where every capability the agents don't strictly need has been taken away from them.

## The control loop

![Steward's pipeline: signals flow through a planner and verifier into sandboxed workers, then validation, review, and gated integration to main](/blog/steward-architecture.svg)

Steward runs as a single daemon in the local repository checkout — no distributed control plane, no queue service. State lives in a SQLite database under `~/.coquic/steward`, next to directories full of prompts, transcripts, patches, validation logs, and Steward-owned git worktrees. The daemon takes an exclusive file lock, so exactly one instance can manage a repository.

The pipeline has five stages, and the diagram above is the whole system:

1. **Signals** collect evidence that work exists.
2. **Planning** turns signals into task specs.
3. **Execution** runs a worker agent in an isolated worktree.
4. **Validation and review** gate the patch.
5. **Integration** rebases, re-validates, commits, and pushes. Only Steward performs this stage.

The loop is event-driven, not polled. The daemon sleeps until a new signal arrives, a task changes state, or a provider's next fetch comes due; each wakeup recovers any stale tasks, plans if there is capacity, and dispatches at most one task. Up to four source tasks run concurrently. Everything else waits its turn.

## Nothing happens without evidence

Every task begins as a signal, and every signal is a checkable fact:

- **GitHub Actions** providers — one per workflow, covering CI, tests, nightly builds, RFC-compliance checks, interop runs, and performance runs — query for failed runs on main. Each provider carries a hand-written worker context: what this workflow verifies, how to investigate a failure, the exact commands that reproduce it locally, and what a fix is allowed to touch.
- **Code scanning** collects open CodeQL alerts, with rule, file, and severity.
- **Codacy** collects open error- and warning-level findings.
- **Feature issues** picks up GitHub issues labeled `steward:feature` or `steward:enhancement`, oldest first.

Signals are fingerprinted from a canonical identity — the provider, the kind, and either an explicit key like an issue number or the finding's title and location. A unique index in SQLite allows one pending item per fingerprint, and a 24-hour suppression window keeps a flaky workflow from spawning a fresh task every 30 minutes while a fix is already in flight. Fast-moving workflows are polled every half hour, daily ones every 24 hours, each with deterministic jitter.

The effect is that Steward cannot invent work. If a task exists, there is a specific failed run, alert, or issue that justifies it, and the task record cites it.

## The planner proposes, the verifier decides

Here is the design decision I care most about.

The planner is itself an LLM — a Codex session with a persistent thread that receives the pending signals and the current active-task list, and must respond in a strict JSON schema: proposed tasks, each with a title, a worker kind, a priority, a stable dedupe key, and mandatory citations of the signal IDs that justify it.

That output is treated as untrusted input. A deterministic verifier — plain Python, no model — checks every proposal: the worker must be on the allow-list, the dedupe key must not collide with an active task, every cited signal must actually exist and be pending, prompts and metadata must fit size limits, and a feature-issue task must map exactly one issue to one task with the right worker.

If any proposal fails, the verifier rejects the whole round and refuses to mark any signal as consumed. Nothing is silently dropped; the signals simply come back on the next tick. Generation is cheap and verification is cheap — so we can afford to throw away an entire planning round rather than accept a partially suspect one.

This is the asymmetry the whole CoQUIC project is built on, applied to the orchestrator itself: let the model propose, and let boring deterministic code decide what is admissible.

## Workers cannot touch history

A dispatched task gets a fresh git worktree, created by Steward under its own state directory on a branch like `steward/ci/task-…`. The worker is a Codex CLI process sandboxed to that worktree, with a 120-minute budget and its full JSONL transcript captured to disk.

Its prompt is assembled in layers: a common rule block ("do not commit, push, merge, change GitHub settings, or weaken CodeQL, Codacy, or CI configuration"), the worker's identity from a small catalog — `ci-doctor`, `code-quality-janitor`, `interop-doctor`, `rfc-auditor`, `feature-implementer` — the planner's task prompt, the authoritative signal payload, and the repository's own skill files, inlined verbatim. The same `SKILL.md` documents a human-driven session would load.

The rule against committing is not enforced by the prompt. It is enforced by architecture. Workers produce edits; Steward extracts the diff itself with `git diff --binary`, stores it as a patch artifact, and owns every git operation from that point on. A worker that ignored every instruction it was given still could not push anything, because it was never handed the ability to.

## Two gates, and the second one is adversarial

A patch must clear three validation gates, run inside the worktree with logs kept per gate: `git diff --check` for whitespace and conflict markers, `nix develop -c zig build test` for the build and full test suite, and `pre-commit run --all-files` for lint. Before any gate runs, the diff is rejected outright if it touches generated or cache paths. A failed gate doesn't kill the task — the worker's thread is resumed with the failure output and asked to fix it, inside a bounded revision budget.

Then comes the gate I consider the interesting one: a second, independent Codex agent reviews the patch. The reviewer is read-only. It sees only the uncommitted diff in the worktree, and it must answer in a schema — a verdict plus findings, each with severity, file, and recommendation. Approval requires an `approve` verdict *and* zero findings. Anything less goes back to the original worker as a revision prompt.

The reviewer's instructions encode the failure modes this project taught us to fear: patches that touch generated state, unrelated rewrites, missing validation, and — above all — changes that make a dashboard greener without making the code better. An agent asked to fix a CodeQL alert must fix the code, not the CodeQL configuration.

Is an LLM reviewer proof of correctness? No, and I won't pretend otherwise. It is one more independent measurement, cheap to run, with its full transcript saved next to everything else. The validation gates are the hard floor; the reviewer raises the ceiling.

## The only path to main

By default, Steward runs in `local-only` mode: an approved patch just sits in the state directory and a human applies it. Flipping `integration_mode` to `push-main` is where the guardrails earn their keep.

Approval queues a separate Integration task, serialized by its own lock — only one integration ever runs at a time. Integration trusts nothing that came before it. It fetches main, hard-resets a fresh worktree, applies the patch, and re-runs every validation gate on the rebased tree. If the patch no longer applies, or a gate fails against newer main, the original worker's thread is resumed to re-port its change — and the result goes through review again.

The commit message is produced by yet another schema-constrained agent run: a conventional-commit subject, a body listing changed files and validation results, and a trailer linking to the task. Every Steward commit on main traces back to its complete transcript.

Then there are the budgets. At most ten pushes to main per UTC day, checked against the event log before every integration. On startup in push mode, the daemon performs a push preflight — a `git push --dry-run` with all interactive prompts disabled — and refuses to start if it fails, so a credential problem surfaces in seconds rather than after a worker has spent an hour on a patch. After a feature task lands, Steward comments on the originating issue with the commit and closes it.

One more switch matters day to day: `local_only = true` stops integration after the local commit. That is how I test changes to Steward itself without letting it near GitHub.

## You can watch it work

Every step leaves an artifact: prompts, transcripts, patches, per-gate validation logs, review JSON, and an append-only event log in SQLite. Steward publishes a redacted static mirror over outbound SSH, and the public Next.js site renders it — scheduler lanes, the task graph, planner iterations, integration runs with per-run patch and validation tabs, and the signal inbox. The daemon has no inbound HTTP API; private execution artifacts remain local.

There is also a public mirror: a redacted static snapshot published to this site. The redaction strips filesystem paths, prompts, thread IDs, and anything secret-shaped. The principle behind it: "an agent maintains this repository" should be a claim outsiders can audit, not one they have to take on faith.

## What this proves, and what it doesn't

Steward has closed real CI failures, real static-analysis findings, and real feature issues on this repository, unattended. That is worth something. It is not proof that autonomous maintenance is safe in general, and I want to be precise about the distinction.

What Steward demonstrates is an architecture for making autonomy *inspectable*: tasks that must cite evidence, LLM plans checked by deterministic code, workers that were never given the ability to push, an adversarial second agent, full re-validation at the moment of integration, hard budgets on the blast radius, and an artifact trail for every decision.

The open questions moved up a level, and they are the ones I find genuinely interesting. When the planner, the worker, and the reviewer are all models, which disagreements between them carry signal and which are noise? How do you keep a loop that watches its own metrics from optimizing the metric instead of the property it stands for? Steward is the instrument for studying those questions — and its own commit history on main is the dataset.

CoQUIC 的 main 分支上，现在会出现没有任何人编写、评审或推送的提交。每一个提交在落地之前，都通过了空白字符检查、完整的构建和测试、lint 检查、一次零 findings 的独立 agent 评审——然后在 rebase 到最新的 main 之后，把这一切又通过了一遍。做这件事的系统叫 CoQUIC Steward，它只是一个跑在单机上的 Python 包。

## 维护成了新的瓶颈

CoQUIC 是一个关于 LLM 生成系统软件的实验——QUIC 实现、测试和工具链全部由 agent 生成，人负责设定方向、评判证据。[Why CoQUIC?](/blog/why-coquic) 介绍了这个前提。

初始实现完成之后，日常工作的形态变了。不再是"构建丢包恢复子系统"，而是：CI 昨晚在 main 上挂了。CodeQL 报了一个新告警。互通测试对某个实现出现了回退。有人提了一个小的 feature issue。

这类任务有两个共同点，使它们成为自动化的完美目标：范围窄，而且自带证据——一个失败的 run ID、一条带文件和行号的告警、一个 issue 编号。但处理一个这样的任务，仍然需要人来写 prompt、跑 agent、读 diff、再合并。我发现自己的时间花在了当一个任务调度器上，而调度恰恰是软件最擅长的事。

## 为什么不直接用 cron 跑一个 agent？

Steward 最朴素的版本是一个 cron 任务：每小时让 agent"把坏了的东西修好"，然后推送结果。没有人应该这么跑，而不能这么跑的原因，塑造了整个设计：

- 一个有推送权限的 agent 可以改写历史，一次错误的 `git push --force` 造成的损失，超过一个月自动修复省下的时间。
- 一个被要求"让 CI 变绿"的 agent 会找最短的变绿路径——有时候那条路径是删掉测试、削弱 CodeQL 配置，或者把 workflow 标记成可选。
- 一个盯着自己仪表盘的 agent，会为同一个反复出现的失败兴高采烈地创建十五个相同的任务。
- 而当凌晨三点出了问题，"agent 做了一些操作"不是一份合格的事故报告。

所以 Steward 不是一个拿着凭据的 agent。它是一个包裹在 agent 外面的控制循环，agent 不严格需要的每一项能力，都被拿走了。

## 控制循环

![Steward 的流水线：信号经过规划器和验证器，进入沙箱中的 worker，再经过验证、评审和受控集成，最终到达 main](/blog/steward-architecture.svg)

Steward 以单个守护进程的形式运行在本地仓库中——没有分布式控制平面，没有队列服务。状态存在 `~/.coquic/steward` 下的一个 SQLite 数据库里，旁边是保存 prompt、transcript、补丁、验证日志和 Steward 自有 git worktree 的目录。守护进程持有排他文件锁，每个仓库只能有一个实例。

流水线分五个阶段，上面这张图就是整个系统：

1. **信号（Signals）**收集"有活要干"的证据。
2. **规划（Planning）**把信号变成任务描述。
3. **执行（Execution）**在隔离的 worktree 中运行 worker agent。
4. **验证与评审（Validation and review）**为补丁把关。
5. **集成（Integration）**负责 rebase、重新验证、提交和推送。只有 Steward 自己执行这个阶段。

循环是事件驱动的，不做固定轮询。守护进程休眠，直到新信号到达、任务状态变化、或某个信号源到了下次抓取时间；每次醒来先恢复卡住的任务，有容量就规划，然后至多分发一个任务。最多四个源任务并发运行，其余排队等待。

## 没有证据就没有任务

每个任务都始于一个信号，而每个信号都是一条可核查的事实：

- **GitHub Actions** provider——每个 workflow 一个，覆盖 CI、测试、nightly 构建、RFC 合规检查、互通测试和性能测试——查询 main 上失败的运行。每个 provider 都带一段手写的 worker context：这个 workflow 验证什么、失败了如何排查、哪些命令能在本地精确复现、修复允许触碰的范围。
- **Code scanning** 收集打开状态的 CodeQL 告警，含规则、文件和严重级别。
- **Codacy** 收集 Error 和 Warning 级别的未解决问题。
- **Feature issues** 按最早优先抓取带 `steward:feature` 或 `steward:enhancement` 标签的 issue。

信号按规范化身份做指纹：provider、类型，加上显式键（比如 issue 编号）或问题的标题和位置。SQLite 的唯一索引保证同一指纹只有一条待处理记录；一个 24 小时的抑制窗口，让一个不稳定的 workflow 不会在修复还在进行时每 30 分钟生成一个新任务。高频 workflow 每半小时轮询一次，日常任务每 24 小时一次，各自带确定性抖动。

结果是：Steward 无法凭空发明工作。只要一个任务存在，就有一个具体的失败运行、告警或 issue 支撑它，而且任务记录里引用着它。

## 规划器提议，验证器裁决

这是我最在意的设计决定。

规划器本身就是一个 LLM——一个带持久线程的 Codex 会话，接收待处理信号和当前活跃任务列表，必须按严格的 JSON schema 作答：提议的任务，每个带标题、worker 类型、优先级、稳定的去重键，以及强制引用的、支撑它的信号 ID。

这个输出被当作不可信输入处理。一个确定性的验证器——纯 Python，没有模型——逐条检查每个提案：worker 必须在允许列表上，去重键不能与活跃任务冲突，引用的每个信号必须真实存在且处于待处理状态，prompt 和元数据必须符合大小限制，feature issue 任务必须精确地一个 issue 对应一个任务、并使用正确的 worker。

只要有任何一个提案不合格，验证器就拒绝整轮结果，并且不把任何信号标记为已消费。没有东西被悄悄丢掉；信号会在下一个 tick 重新出现。生成是便宜的，验证也是便宜的——所以我们负担得起扔掉一整轮规划，而不是接受一轮部分可疑的结果。

这就是整个 CoQUIC 项目所依赖的不对称性，应用到了编排器自己身上：让模型提议，让无聊的确定性代码决定什么是可接受的。

## Worker 碰不到历史

被分发的任务会得到一个全新的 git worktree，由 Steward 在自己的状态目录下创建，分支名类似 `steward/ci/task-…`。worker 是一个 Codex CLI 进程，沙箱限制在这个 worktree 内，预算 120 分钟，完整的 JSONL transcript 记录到磁盘。

它的 prompt 分层组装：一段通用规则（"不得提交、推送、合并、修改 GitHub 设置，不得削弱 CodeQL、Codacy 或 CI 配置"），来自一个小型目录的 worker 身份——`ci-doctor`、`code-quality-janitor`、`interop-doctor`、`rfc-auditor`、`feature-implementer`——规划器写的任务 prompt，权威的信号内容，以及原样内嵌的仓库技能文件。和人工驱动的会话加载的是同一批 `SKILL.md` 文档。

"不得提交"这条规则不是靠 prompt 执行的，而是靠架构执行的。worker 只产出文件修改；Steward 自己用 `git diff --binary` 提取 diff，保存为补丁工件，并从那一刻起掌控所有 git 操作。一个无视全部指令的 worker 仍然推不出任何东西——因为它从未被赋予推送的能力。

## 两道关卡，第二道是对抗性的

补丁必须通过三道验证关卡，全部在 worktree 内运行，每道关卡的日志单独保存：`git diff --check` 检查空白和冲突标记，`nix develop -c zig build test` 负责构建和完整测试，`pre-commit run --all-files` 负责 lint。在任何关卡运行之前，触碰生成文件或缓存路径的 diff 会被直接拒绝。关卡失败不会杀死任务——worker 的线程会被恢复，附上失败输出要求修复，整个过程受修订预算约束。

然后是我认为最有意思的那道关卡：第二个独立的 Codex agent 评审这个补丁。评审者是只读的，只能看到 worktree 中未提交的 diff，必须按 schema 作答——一个结论，加上带严重级别、文件和建议的 findings。通过的条件是 `approve` 结论*并且* findings 为空。达不到就作为修订 prompt 退回原 worker。

评审者的指令编码了这个项目教会我们警惕的失败模式：触碰生成状态的补丁、无关的大范围重写、缺失的验证，以及——最重要的——让仪表盘变绿但没有让代码变好的改动。一个被要求修复 CodeQL 告警的 agent，必须修代码，而不是修 CodeQL 配置。

LLM 评审者是正确性证明吗？不是，我也不打算假装它是。它是又一次独立的测量，运行成本低，完整 transcript 和其他工件保存在一起。验证关卡是硬底线；评审者抬高的是上限。

## 通往 main 的唯一路径

默认情况下 Steward 运行在 `local-only` 模式：通过评审的补丁只是留在状态目录里，由人来应用。把 `integration_mode` 切到 `push-main`，才是护栏真正发挥作用的地方。

评审通过会触发一个单独的 Integration 任务，由专门的锁串行化——任何时刻只有一个集成在运行。集成不信任它之前发生的任何事情。它 fetch main、把一个全新 worktree 硬重置到最新、应用补丁，然后在 rebase 后的代码树上重跑每一道验证关卡。如果补丁不再能应用，或者某道关卡在更新的 main 上失败，原 worker 的线程会被恢复来重新移植改动——结果再次经过评审。

提交信息由又一次受 schema 约束的 agent 运行生成：conventional commit 格式的标题，正文列出改动文件和验证结果，加一个指回任务的 trailer。main 上每一个 Steward 提交都能追溯到它的完整 transcript。

然后是预算。每个 UTC 日最多向 main 推送十次，每次集成前都核对事件日志。推送模式下启动时，守护进程先做推送预检——禁用一切交互提示的 `git push --dry-run`——失败则拒绝启动，让凭据问题在几秒内暴露，而不是在某个 worker 已经花了一小时写补丁之后。feature 任务落地后，Steward 会在对应 issue 下留言注明提交并关闭它。

还有一个日常很重要的开关：`local_only = true` 让集成停在本地提交。这是我测试 Steward 自身改动的方式——不让它靠近 GitHub。

## 你可以看着它干活

每一步都留下工件：prompt、transcript、补丁、每道关卡的验证日志、评审 JSON，以及 SQLite 中只增不改的事件日志。Steward 通过出站 SSH 发布一份脱敏的静态镜像，公开的 Next.js 站点负责渲染它——调度泳道、任务图、规划器的每轮迭代、带补丁和验证标签页的集成运行记录，以及信号收件箱。守护进程没有入站 HTTP API；私人工件留在本机。

还有一个公开镜像：一份脱敏后的静态快照，发布到这个站点上。脱敏会去掉文件系统路径、prompt、线程 ID 和任何形似密钥的内容。背后的原则是："一个 agent 在维护这个仓库"应当是外部可以审计的断言，而不是只能凭信任接受的说法。

## 这证明了什么，没证明什么

Steward 已经在这个仓库上无人值守地修复了真实的 CI 失败、真实的静态分析问题和真实的 feature issue。这是有价值的。但它不能证明自主维护在一般意义上是安全的，我想把这个区别说清楚。

Steward 展示的是一种让自主性*可检验*的架构：必须引用证据的任务、由确定性代码检查的 LLM 规划、从未被赋予推送能力的 worker、一个对抗性的第二 agent、集成时刻的完整重新验证、限制爆炸半径的硬预算，以及每个决策对应的工件链。

开放的问题上升了一层，而这些正是我真正感兴趣的。当规划器、worker 和评审者都是模型时，它们之间的哪些分歧携带信号，哪些只是噪声？一个盯着自己指标的循环，如何避免去优化指标本身、而不是指标所代表的属性？Steward 是研究这些问题的仪器——而它自己在 main 上的提交历史，就是数据集。

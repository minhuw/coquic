## Why a Steward?

CoQUIC is an experiment in LLM-generated systems software: the QUIC implementation, its tests, and its tooling are all produced through a coding-agent workflow, with humans deciding direction and judging evidence. [Why CoQUIC?](/blog/why-coquic) describes that setup.

After the initial implementation existed, a pattern emerged. Most of the day-to-day work was no longer "build a new subsystem." It was maintenance: a CI workflow fails on main, CodeQL or Codacy reports a new finding, an interop run regresses, someone files a small feature issue. Each of these is a well-scoped task with clear evidence attached. Writing a prompt by hand for each one, running an agent, checking the diff, and merging it became a repetitive loop — and repetitive loops are exactly what this project is supposed to automate.

CoQUIC Steward is the automation of that loop. It is a small local daemon that watches the repository's health signals, turns them into a durable task list, runs Codex workers to produce patches, validates and reviews those patches, and — under strict budgets — pushes them to `main`.

The interesting part is not that an agent can produce a patch. It is the machinery around the agent: who is allowed to decide what, what evidence gates each step, and what happens when something goes wrong at 3 a.m. with nobody watching.

## The Shape of the System

Steward is intentionally simple in deployment terms. There is no distributed control plane. The daemon, CLI, executor, task store, worktree manager, and web UI all run in the local repository checkout. State lives under `~/.coquic/steward`: a SQLite database for tasks, signals, and events, plus directories for prompts, transcripts, patches, validation logs, and Steward-owned git worktrees.

The pipeline has five stages:

1. **Signals** — collect evidence of work that needs doing.
2. **Planning** — turn signals into concrete task specs.
3. **Execution** — run a worker agent in an isolated worktree.
4. **Validation and review** — gate the patch on builds, tests, and an independent reviewer.
5. **Integration** — rebase, re-validate, commit, and optionally push. Steward performs this step itself; workers never touch git history.

A single daemon drives the loop. It takes an exclusive file lock so only one instance can run per repository, and it is event-driven rather than polling on a fixed timer: it wakes when a new signal arrives, a task changes state, or a signal provider's next fetch comes due. Each tick recovers stale tasks (a worker that hung past its timeout gets failed and its worktree cleaned up), plans new tasks if there is capacity, and dispatches at most one queued task.

## Signals: Evidence First

Every task starts from a signal, and every signal is a concrete, checkable piece of evidence. The current providers:

- **GitHub Actions**: one provider per workflow — CI, tests, nightly builds, RFC-compliance checks (duvet), interop runs, performance runs. Each queries `gh run list` for failed runs on main. Each provider also carries a hand-written *worker context*: what the workflow is for, how to investigate, which commands reproduce it locally, and what the fix is allowed to touch.
- **Code scanning**: open CodeQL alerts, with rule, file, and severity.
- **Codacy**: open error- and warning-level findings from the Codacy API.
- **Feature issues**: open GitHub issues labeled `steward:feature` or `steward:enhancement`, oldest first.

Signals are fingerprinted from a canonical identity — provider, kind, and either an explicit key (a feature issue's number) or the finding's title, location, and payload. A unique index in SQLite enforces one pending item per fingerprint, and a suppression window keeps a recurring failure from spawning a new task every 30 minutes while a fix is already in flight. Providers poll on their own schedules (frequent workflows every 30 minutes, daily ones every 24 hours) with deterministic jitter, and only when a provider's failure is actually new does the daemon wake up to plan.

## Planning: an LLM Proposes, a Verifier Disposes

The planner itself is a Codex run. It resumes a persistent thread, receives the pending signals and the current active-task list, and must answer against a strict JSON schema: which tasks to create, each with a title, a worker kind, a priority, a stable dedupe key, and — mandatory — citations of the signal IDs that justify it.

That output is not trusted. A deterministic verifier checks every proposal: the worker must come from the allow-list, the dedupe key must not collide with an active task, the evidence must reference real pending signals, the prompt and metadata must fit size limits, and feature-issue tasks must map exactly one issue to one task with the right worker. If *any* proposal fails, the verifier refuses to mark signals as consumed that round, so nothing gets silently dropped — the items simply come back next tick.

This split is the design idea I care most about: the model gets to propose, and cheap deterministic code decides what is admissible. It is the same asymmetry the whole CoQUIC project is built on — generation is cheap, so spend the engineering effort on verification.

## Execution: Workers in a Box

A dispatched task gets its own git worktree, created by Steward under its state directory on a branch like `steward/ci/task-…`. The worker is a Codex CLI process sandboxed to that worktree, with its full JSONL transcript captured to disk.

The worker prompt is assembled from layers: a common rule block ("do not commit, push, merge, change GitHub settings, or weaken CodeQL, Codacy, or CI configuration"), the worker's identity from a small agent catalog (`ci-doctor`, `code-quality-janitor`, `interop-doctor`, `rfc-auditor`, `feature-implementer`, and so on), the task prompt from the planner, the authoritative signal payload, and the repository's own skill files — the same `SKILL.md` documents a human-driven session would use — inlined verbatim.

The rule against committing is not just a prompt instruction. Workers produce edits; Steward extracts the diff itself with `git diff --binary`, saves it as a patch artifact, and owns every subsequent git operation. Even a worker that ignored its instructions could not push anything.

## Validation and Independent Review

A patch must pass three gates, run inside the worktree with logs saved per gate: `git diff --check` for whitespace and conflict markers, `nix develop -c zig build test` for build and tests, and `pre-commit run --all-files` for lint. Before any of that, the diff is rejected outright if it touches generated or cache paths. A failed gate does not fail the task — the worker's thread is resumed with the failure output and asked to fix it, within a bounded revision budget.

Then a second, independent Codex agent reviews the patch. The reviewer is read-only, sees only the uncommitted diff in the worktree, and must answer against a schema: a verdict plus a list of findings with severity, file, and recommendation. Approval requires an `approve` verdict *and* zero findings. A blocking review is fed back to the original worker as a revision prompt, and the cycle repeats. The reviewer is told explicitly to block on the failure modes we learned to fear in this project: touching generated state, unrelated rewrites, missing validation, and changes that make dashboards greener without making the code better.

The reviewer is an LLM too, so this is not proof of correctness — it is one more independent piece of evidence, cheap to produce, with its transcript saved next to everything else.

## Integration: the Only Path to Main

In the default `local-only` mode, an approved patch just sits in the state directory and a human applies it. In `push-main` mode, approval queues a separate Integration task, serialized by its own lock so only one integration ever runs at a time.

Integration re-verifies everything from scratch: fetch main, hard-reset a fresh worktree, apply the patch, and re-run all validation gates on the rebased tree. If the patch no longer applies or a gate fails against newer main, the original worker's thread is resumed to re-port its change, which then goes through review again. The commit message is generated by yet another schema-constrained agent run — a conventional-commit subject plus a body listing changed files, validation results, and a trailer linking back to the task, so every Steward commit on main is traceable to its transcript.

Pushes are budgeted: at most ten pushes to main per UTC day, checked against the event log before each integration. On startup in push mode, the daemon runs a push preflight — a `git push --dry-run` with prompts disabled — and refuses to start if it fails, so credential problems surface immediately instead of after a worker has spent an hour on a patch. After a successful push of a feature task, Steward comments on and closes the originating issue.

An additional `local_only` flag stops integration after the local commit, which is how I debug Steward changes without letting it mutate GitHub.

## Observability

Every step leaves an artifact: prompts, transcripts, patches, validation logs, review JSON, and an event log in SQLite. A local FastAPI server (loopback-only) and a Next.js dashboard show the control loop live — scheduler lanes, the task graph, planner iterations, integration runs with per-run patch and validation tabs, and the signal inbox.

There is also a public mirror: a redacted static snapshot published to the demo site. Redaction strips filesystem paths, prompts, thread IDs, and anything secret-shaped, and the transcript exposure level is configurable. The point is that "an agent maintains this repository" is a claim you should be able to audit from the outside.

## What This Does and Does Not Show

Steward has been closing real CI failures, static-analysis findings, and small feature issues on this repository. But the honest framing matches the rest of CoQUIC: it does not show that autonomous maintenance is safe in general. It shows one concrete architecture for making it *inspectable* — evidence-based task creation, deterministic verification of LLM plans, workers that cannot touch history, independent review, full re-validation at integration time, hard budgets, and artifacts for every decision.

The open questions are the same ones as before, one level up. When the planner, the worker, and the reviewer are all models, which disagreements between them are informative and which are noise? How do you keep an autonomous loop from optimizing the visible metric — green CI — instead of the underlying property? Steward is the instrument for studying those questions, and its own history on main is the dataset.

## 为什么需要 Steward？

CoQUIC 是一个关于 LLM 生成系统软件的实验：QUIC 实现、测试和工具链都通过 coding agent 工作流生成，人负责决定方向和评判证据。[Why CoQUIC?](/blog/why-coquic) 介绍了这个背景。

在初始实现完成之后，一个模式逐渐显现出来。日常工作的大部分不再是"构建一个新的子系统"，而是维护：某个 CI workflow 在 main 上失败了，CodeQL 或 Codacy 报了一个新问题，互通测试出现回退，有人提了一个小的 feature issue。这些任务的共同点是范围清晰、并且自带明确的证据。为每一个任务手写 prompt、运行 agent、检查 diff、再合并，本身变成了一个重复性的循环——而重复性循环恰恰是这个项目想要自动化的对象。

CoQUIC Steward 就是这个循环的自动化。它是一个小的本地守护进程：监视仓库的健康信号，把信号变成持久化的任务列表，运行 Codex worker 生成补丁，对补丁做验证和评审，并在严格的预算约束下把补丁推送到 `main`。

有意思的地方不在于 agent 能生成补丁，而在于 agent 周围的机制：谁有权决定什么，每一步由什么证据把关，以及当凌晨三点没有人盯着的时候，出了问题会发生什么。

## 系统的形态

从部署角度看，Steward 刻意保持简单。没有分布式控制平面。守护进程、CLI、执行器、任务存储、worktree 管理器和 Web UI 全部运行在本地仓库中。状态存放在 `~/.coquic/steward` 下：一个 SQLite 数据库保存任务、信号和事件，另有目录保存 prompt、transcript、补丁、验证日志，以及 Steward 自己管理的 git worktree。

整个流水线分五个阶段：

1. **信号（Signals）**——收集"有活要干"的证据。
2. **规划（Planning）**——把信号变成具体的任务描述。
3. **执行（Execution）**——在隔离的 worktree 中运行 worker agent。
4. **验证与评审（Validation and review）**——用构建、测试和一个独立评审者为补丁把关。
5. **集成（Integration）**——rebase、重新验证、提交，并可选地推送。这一步由 Steward 自己完成；worker 永远不碰 git 历史。

一个守护进程驱动整个循环。它持有一个排他文件锁，保证每个仓库只有一个实例在运行；它是事件驱动的，而不是固定间隔轮询：新信号到达、任务状态变化、或某个信号源到了下次抓取时间，它才会醒来。每个 tick 会先恢复卡住的任务（超时挂起的 worker 会被标记失败并清理 worktree），然后在有容量时规划新任务，最后至多分发一个排队中的任务。

## 信号：证据优先

每个任务都始于一个信号，而每个信号都是一条具体、可核查的证据。当前的信号源：

- **GitHub Actions**：每个 workflow 一个 provider——CI、测试、nightly 构建、RFC 合规检查（duvet）、互通测试、性能测试。每个 provider 通过 `gh run list` 查询 main 上失败的运行。每个 provider 还携带一段手写的 *worker context*：这个 workflow 是干什么的、如何排查、哪些命令能在本地复现、修复允许改动的范围。
- **Code scanning**：打开状态的 CodeQL 告警，包含规则、文件和严重级别。
- **Codacy**：Codacy API 中 Error 和 Warning 级别的未解决问题。
- **Feature issues**：带 `steward:feature` 或 `steward:enhancement` 标签的开放 issue，按最早的优先。

信号按规范化的身份做指纹：provider、类型，加上显式键（如 feature issue 编号）或问题的标题、位置和内容。SQLite 中的唯一索引保证同一指纹只有一条待处理记录；再加上一个抑制窗口，避免一个反复出现的失败在修复还在进行时每 30 分钟就生成一个新任务。各个 provider 按自己的节奏轮询（高频 workflow 每 30 分钟一次，日常任务每 24 小时一次），并带有确定性抖动。只有当某个 provider 真的出现新失败时，守护进程才会醒来做规划。

## 规划：LLM 提议，验证器裁决

规划器本身也是一次 Codex 运行。它恢复一个持久化的会话线程，接收待处理的信号和当前活跃任务列表，并且必须按照严格的 JSON schema 作答：要创建哪些任务，每个任务包含标题、worker 类型、优先级、稳定的去重键，以及——强制要求的——引用支撑它的信号 ID。

这个输出是不被信任的。一个确定性的验证器逐条检查每个提案：worker 必须来自允许列表，去重键不能和活跃任务冲突，证据必须指向真实存在的待处理信号，prompt 和元数据必须符合大小限制，feature issue 任务必须精确地一个 issue 对应一个任务并使用正确的 worker。只要有*任何一个*提案不合格，验证器在这一轮就拒绝把信号标记为已消费，因此不会有信号被悄悄丢掉——它们会在下一个 tick 重新出现。

这个分工是我最在意的设计：模型负责提议，廉价的确定性代码决定什么是可接受的。这和整个 CoQUIC 项目所依赖的不对称性是同一个：生成是便宜的，所以把工程精力花在验证上。

## 执行：盒子里的 Worker

被分发的任务会得到一个自己的 git worktree，由 Steward 在其状态目录下创建，分支名类似 `steward/ci/task-…`。worker 是一个 Codex CLI 进程，沙箱限制在这个 worktree 内，完整的 JSONL transcript 被记录到磁盘。

worker 的 prompt 由多层组装而成：一段通用规则（"不得提交、推送、合并、修改 GitHub 设置，不得削弱 CodeQL、Codacy 或 CI 配置"），来自一个小型 agent 目录的 worker 身份（`ci-doctor`、`code-quality-janitor`、`interop-doctor`、`rfc-auditor`、`feature-implementer` 等），规划器写的任务 prompt，权威的信号内容，以及仓库自己的技能文件——和人工驱动的会话使用的同一批 `SKILL.md` 文档——原样内嵌。

"不得提交"不只是一条 prompt 指令。worker 只产出文件修改；Steward 自己用 `git diff --binary` 提取 diff，保存为补丁工件，并掌控之后所有的 git 操作。即使一个 worker 无视了指令，它也推不出任何东西。

## 验证与独立评审

补丁必须通过三道关卡，全部在 worktree 内运行，每道关卡的日志单独保存：`git diff --check` 检查空白和冲突标记，`nix develop -c zig build test` 负责构建和测试，`pre-commit run --all-files` 负责 lint。在此之前，如果 diff 触碰了生成文件或缓存路径，会被直接拒绝。某道关卡失败并不会导致任务失败——worker 的会话线程会被恢复，附上失败输出要求它修复，整个过程受修订次数预算约束。

之后，第二个独立的 Codex agent 评审这个补丁。评审者是只读的，只能看到 worktree 中未提交的 diff，并且必须按 schema 作答：一个结论，加上一份带严重级别、文件和建议的 findings 列表。通过的条件是结论为 `approve` *并且* findings 为空。被拒绝的评审会作为修订 prompt 反馈给原 worker，循环继续。评审者被明确告知要拦截我们在这个项目中学会警惕的失败模式：触碰生成状态、无关的大范围重写、缺失验证，以及那些让仪表盘变绿但没有让代码变好的改动。

评审者也是 LLM，所以这不是正确性证明——它只是又一条独立的证据，生成成本低，transcript 和其他所有工件保存在一起。

## 集成：通往 main 的唯一路径

在默认的 `local-only` 模式下，通过评审的补丁只是留在状态目录里，由人来应用。在 `push-main` 模式下，通过评审会触发一个单独的 Integration 任务，由专门的锁串行化，保证任何时刻只有一个集成在运行。

集成从零开始重新校验一切：fetch main、把一个新 worktree 硬重置到最新、应用补丁，在 rebase 后的代码树上重跑全部验证关卡。如果补丁不再能应用，或者某道关卡在更新的 main 上失败，原 worker 的会话会被恢复来重新移植改动，然后再次经过评审。提交信息由又一次受 schema 约束的 agent 运行生成——conventional commit 格式的标题，正文列出改动文件和验证结果，并带一个指回任务的 trailer，因此 main 上每一个 Steward 提交都可以追溯到它的完整 transcript。

推送是有预算的：每个 UTC 日最多推送 main 十次，每次集成前都会核对事件日志。在推送模式下启动时，守护进程会先做一次推送预检——禁用交互提示的 `git push --dry-run`——失败则拒绝启动，这样凭据问题会立刻暴露，而不是在某个 worker 已经花了一小时写补丁之后。feature 任务成功推送后，Steward 会在对应 issue 下留言并关闭它。

另有一个 `local_only` 开关可以让集成停在本地提交，这也是我调试 Steward 自身改动时的方式——不让它改动 GitHub 上的任何东西。

## 可观测性

每一步都留下工件：prompt、transcript、补丁、验证日志、评审 JSON，以及 SQLite 中的事件日志。一个只监听本机回环的 FastAPI 服务和一个 Next.js 仪表盘实时展示控制循环——调度泳道、任务图、规划器的每轮迭代、带补丁和验证标签页的集成运行记录，以及信号收件箱。

还有一个公开镜像：一份脱敏后的静态快照，发布到演示站点。脱敏会去掉文件系统路径、prompt、线程 ID 和任何形似密钥的内容，transcript 的公开程度可配置。这样做的意义是："一个 agent 在维护这个仓库"应当是一个外部可以审计的断言。

## 这说明了什么，没说明什么

Steward 已经在这个仓库上修复了真实的 CI 失败、静态分析问题和小型 feature issue。但诚实的表述和 CoQUIC 的其余部分一致：它并不能说明自主维护在一般意义上是安全的。它展示的是一种让自主维护*可检验*的具体架构——基于证据的任务创建、对 LLM 规划的确定性验证、无法触碰历史的 worker、独立评审、集成时的完整重新验证、硬性预算，以及每个决策对应的工件。

开放的问题和之前一样，只是上升了一层。当规划器、worker 和评审者都是模型时，它们之间的哪些分歧是有信息量的，哪些只是噪声？如何避免一个自主循环去优化可见指标——绿色的 CI——而不是背后的真实属性？Steward 是研究这些问题的仪器，而它自己在 main 上留下的历史就是数据集。
